# 技术审计报告（2026-11-10）

范围：`trader/`、`trader/intraday/`、`web/api/`、`web/ui/`、`deploy/`、`tests/`、`docs/`，以代码为准，文档只作对照。
运行现场数据来自 Mac mini 的只读查询（ledger `mode=ro`、日志文件），采集时间 2026-11-10 04:54–05:30 UTC。

## 1. 总体评价

项目是上游 TradingAgents（v0.7.1）之上的一层独立加密模拟盘：日频多智能体研判 → 五档评级 → 代码侧定量仓位（Full Position Unit、ATR 止损、熔断），外加一个小时级单模型信号的日内账户（ADR 0006）和一个只读看板（ADR 0005/0007）。

| 维度 | 评价 | 依据 |
|---|---|---|
| 架构 | 良好 | 分层清楚：`rules`（纯函数）→ `paper`（账户状态机）→ `jobs`（调度）→ `__main__`；web 只读、唯一写端点有 ADR；trader 与 tradingagents 以公共接口隔离（ADR 0001，仅一处突破，见 #6） |
| 代码质量 | 良好 | 模块短（最长 601 行）、函数单一职责、文档字符串写明契约；ruff 全仓通过、oxlint 0 警告、tsc 通过 |
| 测试 | 良好 | trader/web 相关 441 个测试 2.6 s 通过；规则层、账户状态机、API 均有覆盖；缺口：OKX 不可达的降级路径、日内失败重试 |
| 可靠性 | 中 | 对外部依赖（OKX、Anthropic）的失败处理是“记录并抛出”，缺少降级：web 3 天内 1,040 次 500（8.7%），日报在 OKX 不可达时发不出，日内账户 11-10 连续 2 小时无决策 |
| 性能 | 良好 | 数据量小（ledger < 100 KB，研究记录 12 个 × 69 KB）；web 3 天 12,004 次请求（≈ 4,000/天），overview+equity 占 75%，TTL 缓存有效；无索引/无 WAL 在当前规模下不构成瓶颈 |
| 安全 | 中 | 无密钥入库（`.env` 已忽略，Telegram 错误不记 token）；路径参数正则校验、SQL 全部参数化；唯一写端点 `POST /api/settings/llm` 无认证却经 tailscale serve 暴露到整个 tailnet（CORS 仅放行 dev 源、JSON-only 使浏览器 CSRF 难成立，但 tailnet 内任何进程可写） |
| 可维护性 | 良好 | ADR 完整；`IntradayPaper(Paper)` 复用 `_move`/`_stop_alert` 两个私有函数、`ledger.py` 反向依赖 `trader.intraday.types`，是仅有的两处耦合味道 |
| 流程 | 弱 | GitHub Issue/PR/CI 均为 0（已补 Issue #1～#10）；CI 只跑 `main`/`v*`，`crypto-trader` 分支从未被 CI 验证（#5） |

结论：**不需要架构级重构**。问题集中在“外部依赖失败时的降级”和“工程流程”，用局部加固解决；策略常量、研判输入和模型在验证期内冻结（ADR 0004），本轮不动。

## 2. 架构

### 2.1 现状

```
            launchd (Mac mini, TZ=UTC)
   daily 00:05(+03:05/06:05)   mark :07 每小时   intraday :03 每小时   web (常驻)
          │                        │                  │                 │
          ▼                        ▼                  ▼                 ▼
   trader.jobs.daily        trader.jobs.mark   trader.intraday.job   web.api.app (FastAPI)
   ├ Researcher ──► tradingagents.graph (公共接口)      ├ Signaler ──► 单个深度模型
   ├ Paper.replay/execute   Paper.replay       ├ IntradayPaper(Paper)   ├ data.py (只读)
   ├ report.daily                              ├ intraday.report        │  ├ Ledger(mode=ro)
   └ Notifier (Telegram)                       └ Notifier               │  ├ Market(OKX, TTL)
          │                        │                  │                 │  └ research 记录文件
          ▼                        ▼                  ▼                 │
   ~/.tradingagents/trader/ledger.sqlite      intraday/ledger.sqlite   └ POST /api/settings/llm
   (flock trader.lock)                        (flock intraday/trader.lock)     └► settings.json
          ▲                        ▲                  ▲                              │
          └───────── OKX 公共行情（K 线、最新价、资金费）─────────┘        两个账户下次运行时读取
```

数据流：研判结果写 `attempts`（日频）/`signals`（日内）→ `execute` 按评级/信号算目标仓位 → `fills`/`positions`/`equity` → web 只读呈现；`settings.json` 是 web 到 trader 的唯一反向通道。

### 2.2 目标（本轮之后）

结构不变，只在三处加“失败边界”：

```
   OKX ──► OKX 客户端 ──► Market 缓存（成功 TTL + 失败短缓存）──► data.py：行情缺失时返回 null 字段 + `market: {ok, error}`，不再 500
   OKX ──► report.daily：最新价取不到时用 ledger 最近标记价并在日报标注“行情暂不可用”，日报必发
   模型 ──► intraday.job：某币信号失败在同一小时内有界重试（2 次、间隔 2 分钟），仍失败才记 None；连续失败 N 小时告警
```

前后对比：对外契约不变（API 字段只增不减，UI 兼容）；账户状态机、规则、指纹不变；新增的全部是“失败时的行为”，可按 Issue 单独回滚。

### 2.3 方案比较（主决策）

| 方案 | 内容 | 收益 | 风险/成本 | 结论 |
|---|---|---|---|---|
| A 保留现有方案并优化 | 在现有模块内加降级、重试、认证、索引、CI | 改动小、可逐项回滚、不碰验证期冻结项 | 耦合味道（私有函数复用、反向依赖）保留，但影响局限 | **采用** |
| B 局部重构 | 抽出 `MarketData` 接口统一 trader/web 的行情获取；把 `_move` 等提为公共 API；ledger 拆读写两类 | 消除两处耦合、便于扩池 | 触及 `paper.py`/`ledger.py` 核心路径，需要大面积回归；验证期内风险不值 | 延后到验证期结束（Issue 记录） |
| C 架构级重构 | 事件驱动/消息队列、服务化、换 DB | 无对应的业务需求 | 单机单用户场景，复杂度与风险远超收益 | 否决 |
