## 基线测量方案

基线的目的，是回答「目前系统在固定条件下表现如何」，然后团队再决定性能和成本目标。**基线数据不是验收阈值**；不要先把某个秒数或 token 数写成正式承诺。

### 1. 固定实验条件

每次记录：

- 源码 commit、Python 和依赖版本
- provider、精确 model ID、prompt/config 版本、温度和重试配置
- ticker、as-of date、分析师集合、研究深度和辩论轮数
- 数据快照或缓存状态（冷缓存、热缓存分开测）
- 运行机器、开始时间及 run ID

真实模型运行可能波动。固定模型和输入能减少干扰；缓存冷、热结果不要混成一个分布。

### 2. 分两种测量

**离线可重复测量**：用固定数据和 fake provider 检查流程、调用计数、token 预算行为、故障状态和安全验证。它适合做 CI 验收，不应拿来代表真实模型的响应时间或成本。

**真实 provider 基线**：选定一个典型标的和日期、固定完整配置，测真实的 wall-clock 时间、输入/输出 token、LLM 调用数、工具调用数、重试、成功/失败状态和费用（若 provider 提供可靠计价数据）。先跑 5 次校准采集，再做约 30 次正式样本；如果要据此设稳定的 p95 目标，样本越多越好。样本少时应同时报告最大值，不要把 p95 说得过于确定。

现有统计回调会累计调用数，并在 provider 返回 `usage_metadata` 时累计 token；若该字段缺失，当前代码不会把缺失用量补成总量。因此报告要把“未知”与零区分。:codex-file-citation{path="/Users/yifeng/Desktop/软工/project/TradingAgents-main/cli/stats_handler.py" purpose="source"}

### 3. 每次运行保存同一组指标

建议输出 CSV 或 JSONL，每行一轮运行，字段至少包括：

```text
run_id, commit, provider, model, prompt_version, config_version,
ticker, as_of_date, cache_mode, elapsed_seconds,
llm_calls, tool_calls, input_tokens, output_tokens,
retry_count, outcome, failure_reason, estimated_cost
```

再按冷缓存/热缓存分别汇总：

- 耗时：p50、p95、最大值
- 调用和 token：中位数、p95、最大值
- 成功、`REVIEW`、`INCOMPLETE` 的比例
- 缺用量数据的运行数量
- 若有固定评估集：质量分数和安全违规次数

### 4. 用结果定目标，并补失败场景

测完后由团队共同决定耗时和 token 的限额，并确认目标是否会损害报告质量。之后用 fake provider 注入超时、缺失 usage、数据源失败、格式错误等情况，验证系统能否停止并给出正确状态，而不是把失败运行当成有效完成。

当前最优先的测量事项，是**选定可重复的典型运行配置，并确认 token usage 在所选 provider 上是否完整可得**。这样才有可靠数据来定 `REQ-TA-NFR-PERF-001` 和 `REQ-TA-NFR-COST-001` 的数值。

## 先定需求，还是先测基线？

建议**先定项目范围，再测基线；用测量结果补完需求，再确定架构**。不建议等所有需求都写得很细、完全冻结之后才测基线，因为运行时间、token 用量、已有能力和代码缺口都会影响需求是否可行、阈值该怎么设。需求工程本身也是迭代的。

架构则应等关键需求和安全规则已经达成一致后再定。此时不必等每个次要需求都毫无疑问，但架构驱动项——尤其是系统边界、确定性安全门和 Must 级需求——必须清楚。
