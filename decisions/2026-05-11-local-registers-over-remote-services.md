# Decision: Local Registers Over Remote Services for Code Intelligence

**Date**: 2026-05-11
**Status**: Active

## Decision

For code-intelligence tooling (symbol indexes, cross-reference, search), use local JSONL registers generated by project-local scripts rather than remote services (MCP servers, Sourcegraph, GitHub Copilot, vector databases).

## Context

The document registry system (5 registries, `reg-sync.ts`, `*/INDEX.jsonl`) is proven, silo-native, and low-cost. When a code-intelligence gap was identified, the instinctive response in most teams is to reach for a remote service. This decision establishes that the same register pattern should apply to code.

## Rationale

**For local registers:**
- No external dependencies (no API keys, no network, no vendor lock-in)
- Silo-native (lives in the project, boots with the project, moves with the project)
- Proven pattern (same implementation as document registries)
- Zero latency (local file read, not HTTP round-trip)
- Agent-legible (JSONL is readable by any agent without a service client)
- Explicit ownership (index generated from codebase, not maintained by external service)

**Against remote services (for this use case):**
- External dependency — service outage, key expiry, or vendor pricing change breaks the system
- Data egress — prompts and code may leave the environment
- Observability gap — the index is maintained by the vendor, not the silo
- Latency — HTTP calls add round-trip time on every query
- Complexity — MCP server, auth, configuration, version management

**Acceptable exceptions:**
- Remote services may be added as an additional layer (e.g., Sourcegraph for large-codebase cross-repo search)
- The local register remains canonical; remote services are supplementary
- If a remote service is preferred for a specific capability, it must not break the local register

## Implementation

- `scripts/code-reg-sync.ts` — ast-grep → `code/INDEX.jsonl` (same pattern as `reg-sync.ts`)
- Integrated into `just check` pipeline
- Document registries remain the reference for the pattern
- Remote services may be evaluated per-capability, not per-problem

## Status

Active. Applies to all future code-intelligence tooling decisions in this silo.
