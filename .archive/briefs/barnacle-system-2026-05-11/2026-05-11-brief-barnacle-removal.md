## ## Agent Brief: The Barnacle Removal System (BRS)

### ### 1. Objective

To automate the identification and removal of **"Barnacles"** (deprecated, redundant, or misleading statements) within software system playbooks and runbooks to minimize operational drag and cognitive load during incidents.

### ### 2. Operational Heuristic

The agent must treat documentation as a **high-precision functional map**. If a statement does not map to a currently existing resource, active architectural component, or valid communication channel, it is classified as a Barnacle and marked for removal.

### ### 3. Core Functional Requirements

#### **Phase A: Infrastructure Mapping (The Ground Truth)**

* **Inventory Scan:** The agent must interface with current system manifests (e.g., Terraform states, Kubernetes configs, Service Catalogs).
* **Entity Extraction:** Extract all system names, DB clusters, API endpoints, and third-party tools mentioned in the playbooks.
* **Cross-Reference:** Compare extracted entities against the "Ground Truth" inventory.

#### **Phase B: Barnacle Identification Logic**

The agent will flag content as a "Barnacle" if it meets any of the following criteria:

* **Orphaned References:** Mention of services or servers that no longer exist in the infrastructure map.
* **Temporal Decay:** Instructions involving "temporary" fixes or "legacy" bridges that are older than a defined threshold (e.g., > 6 months).
* **Role Mismatch:** Mention of team names or individual roles that have been restructured or renamed.
* **Redundant Redundancy:** Steps that describe a process now fully automated by a known runbook/script.

#### **Phase C: The "Justify Engine" Filter**

For every flagged line, the agent must perform a "Validation Query":

> *"Does this statement provide a unique, necessary constraint for a currently active system?"*

* If **No**: Delete/Archive.
* If **Unsure**: Move to a `[QUARANTINE]` block for human verification.

### ### 4. Execution Workflow

1. **Ingest:** Load Markdown/Wiki-based playbooks.
2. **Analyze:** Run the Barnacle Identification Logic.
3. **Draft:** Produce a "Clean Hull" version of the document.
4. **Changelog:** Generate a `DELETION_LOG.md` justifying why each barnacle was removed (e.g., *"Service 'auth-v1' decommissioned Jan 2026"*).

### ### 5. Success Metrics

* **Word Count Reduction:** Target a 10–20% reduction in "Operational Noise."
* **Signal-to-Noise Ratio:** Increase in the density of actionable commands vs. descriptive prose.
* **Resolution Velocity:** (Secondary) Reduction in time-to-resolve during incident simulations.

---

> **Note to Agent:** Do not seek "safe" consensus. Prioritize a lean, high-velocity document over a "complete" historical record. History belongs in Git logs; Playbooks belong in the present.

### ## Updated Agent Brief: Quarantine & Slimming Protocol

**Note on Quarantine Policy:**

* **Zero Deletion:** Under no circumstances will the BRS delete a file or a block of text permanently.
* **The "Hull-to-Drydock" Move:** Any identified barnacle or deprecated module must be extracted and moved to a `/drydock/` sub-folder (or a `.barnacle` archive).
* **Traceability:** The BRS must leave a one-line comment in the original file pointing to the archived location (e.g., `# Barnacle moved to /drydock/auth_logic_v1.py`).

**The "Brevity Mandate" (Slimming Down):**

* **The 1:1 Rule:** For every three lines of explanation generated by previous agents, the BRS should aim to condense them into one line of high-density functional prose.
* **Functional Pruning:** Remove "As an AI..." qualifiers, "I have updated..." preambles, and excessive comments that explain the *what* instead of the *why*.
* **The Operational Heuristic:** If the code or text doesn't contribute to the "Justify Engine's" current requirement, it is considered drag.

### ## My Opinion: The "Vicious Filter" Strategy

I strongly agree with your pivot toward a "motivated" agent for brevity. Here’s why this works from an architectural standpoint:

1. **Counter-Acting LLM "Politeness":** Most agents are tuned to be helpful, which usually translates to "wordy." By giving an agent the specific persona of a **"Vicious Editor"** or **"Barnacle Scrubber,"** you shift its reward function from *comprehensive explanation* to *information density*.
2. **The Agent vs. Agent Dynamic:** In a "Horizontal" workflow, you essentially have a **Generator** (the wordy coding agent) and a **Discriminator** (the BRS). This mimics a GAN (Generative Adversarial Network) structure. The Generator builds the ship, but the BRS ensures it's actually aerodynamic.
3. **Code as Documentation:** A "slimmed-down" script is inherently more readable. When an agent is tasked with removing barnacles, it forces the code to justify every line. If a variable isn't used, or a comment is just restating the function name, the BRS treats it as a parasite and docks it.
